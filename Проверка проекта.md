## Ошибки реализации

### 1 Ручные исправления теряются при повторном парсинге

**Приоритет высокий.** `codex/app/services.py`, функция `upsert_parsed`, строка 22.

Сценарий: исправить примечание записи, затем нажать «Перепарсить». Примечание заменяется исходным значением из файла. Вместе с ним безусловно обновляются название, изделие, параметры, ограничения и статус. Потеря ручного исправления не попадает в журнал.

Проверка воспроизвела потерю правки, новых записей журнала при перезаписи не появилось. Нужно разделить результат парсера и подтвержденные пользователем значения, определить правила слияния и показывать конфликт до перезаписи.

### 2 Некорректный JSON сохраняется и ломает карточку

**Приоритет высокий.** `codex/app/services.py`, строки 144 и 161–162; `get_record`, строка 140.

При редактировании строка параметров, начинающаяся с `{`, сохраняется без проверки JSON. Значение `{broken` попало в SQLite, после чего и сохранение, и открытие карточки вернули HTTP 500 с `JSONDecodeError`.

Нужно разбирать и проверять параметры до записи, возвращать понятную ошибку в форму и отклонять значения, которые не являются объектом параметров. Одна некорректная запись не должна ломать просмотр.

### 3 Создание записи теряет параметры в обещанном формате

**Приоритет высокий.** `codex/app/services.py`, строки 194–207.

Форма предлагает JSON или `key=value; key2=value2`. При создании `power_kw=2; voltage_v=220` превращается в пустой объект `{}`. При редактировании такой формат обрабатывается другой веткой и работает.

Причина: для строки без начальной `{` функция создания сразу выбирает `{}` и не доходит до разбора пар `ключ=значение`. Создание и редактирование должны использовать одну проверенную функцию преобразования параметров.

### 4 Изменение обозначения приводит к дублированию

**Приоритет высокий.** `codex/app/services.py`, строка 50; `codex/app/db.py`, таблица `records`.

Парсер ищет запись по редактируемому `document_id`, хотя связь с исходным стандартом уже хранится в `standard_id`. После ручной смены обозначения и повторного парсинга в проверке появились две записи для одного `standard_id`.

Нужно определить, допускаются ли несколько изделий из одного стандарта. Для текущей модели «один стандарт — одна запись» повторное обновление должно опираться на устойчивую связь с источником. При модели нескольких изделий нужен отдельный устойчивый идентификатор изделия, а не только обозначение документа.

### 5 Ошибочные и пустые загрузки обрабатываются неправильно

**Приоритет высокий.** `codex/app/main.py`, строки 135–140; `codex/app/services.py`, строка 103.

Файл неподдерживаемого типа сначала записывается в `uploads` и `standards`, а затем вызывает HTTP 500. Проверочный `.exe` остался в папке стандартов. Пустой `.txt` был принят и получил статус `parsed` с незаполненными смысловыми полями.

Сервер не ограничивает размер через свою логику и читает файл целиком. Скан без текстового слоя также не получает явного статуса «нужен OCR»: парсер допускает запасные значения. Одинаковое имя загрузки перезаписывает файл без версионирования. Поврежденный PDF или эталон может нарушить расчет точности, который вызывается при открытии страниц.

Нужны проверка типа, размера, читаемости и обязательных полей до фиксации загрузки, отдельные состояния ошибок, безопасные уникальные имена и понятное сообщение пользователю.

### 6 Подборы не проверяют существование записей

**Приоритет средний.** `codex/app/services.py`, строка 235; `codex/app/db.py`, строка 55.

В проверке сохранился подбор с ID `[999999, 999999]`, которых нет в базе. Список ID хранится строкой JSON без внешних ключей. Удаление записи не обновляет сохраненные подборы.

Нужно проверять ID, удалять повторы и выбрать поведение при изменении или удалении записи: хранить снимок результата либо использовать связанные строки таблицы состава подбора с явными правилами удаления.

### 7 Показатель точности не равен качеству базы

**Приоритет высокий для приёмки.** `codex/app/services.py`, строка 275; `codex/scripts/seed_standards.py`.

Расчет повторно парсит файлы рядом с эталонами, а не проверяет сохраненные записи SQLite. Поэтому ручная порча записи и ошибки сохранения не обязаны снижать показатель на панели.

Если исходный файл для эталона отсутствует, пара молча исключается. В проверке после удаления девяти исходников показатель остался 100%, но только на одном документе из десяти. Процент нужно показывать вместе с покрытием эталонного набора и числом пропущенных документов.

Все десять исходников и эталоны созданы одним генератором в формате, удобном для текущих правил. Результат 60/60 подтвержден именно для этих примеров. Качество на реальных документах заказчика, PDF с разметкой и сканах не установлено. Эталон должен независимо проверять специалист по данным или тестировщик.

### 8 Кириллический поиск зависит от регистра

**Приоритет средний.** `codex/app/services.py`, строка 113.

На исходной базе поиск `Насосный` нашёл одну запись, `НАСОСНЫЙ` не нашёл ни одной. Текущий `LIKE` не обеспечивает ожидаемый поиск кириллицы без учета регистра. Нужны единое нормализованное представление для поиска либо подходящий механизм полнотекстового поиска.

### 9 Витрина статуса повторно парсит набор документов

**Приоритет средний.** `codex/app/main.py`, `_ctx`; `codex/app/services.py`, строка 255.

Открытие почти любой HTML-страницы вызывает `status_snapshot`, который заново считает точность на файлах. Страница точности делает такой расчет дополнительно. На большом наборе это лишняя работа, а ошибка чтения одного оценочного файла может затронуть страницы, которые от него не зависят.

Стоит запускать замер отдельно, сохранять последний результат и отображать дату, набор документов и ошибки последнего прогона. Замеры производительности в этой проверке не проводились.

## Исходные находки по согласованности документов и плана

1. **Сроки допускают объяснение через резерв, но это не подписано.** Устав и слайды 1 и 15 задают предельный срок 20.12.2026. MPP и слайд 8 заканчиваются 16.12.2026. Можно оставить 16 декабря плановой датой, а 20 декабря предельной, явно указав четырехдневный календарный резерв. На слайде 7 старт обозначен как «20 сентября», тогда как устав и MPP начинаются 24 сентября.
2. **Архитектура смешивает готовую и целевую функциональность.** На слайде 13 показаны OCR и выгрузка, хотя реестр требований отмечает OCR как несделанный, а подборы как частично выполненные. Нужно подписать целевое состояние или отметить незавершенные блоки.
3. **Фактический прогресс в плане не отражен.** У всех 58 задач MPP стоит 0%, хотя презентация на 05.11 отмечает ряд требований выполненными. Это не доказательство отсутствия выполненной работы. Нужно внести подтвержденный прогресс и дату статуса, не подменяя факт плановыми датами.
4. **Поиск зависит от OCR без очевидной необходимости.** В MPP задача 38 «Серверная часть поиска и фильтрации» зависит от задачи 28 «Подключение OCR». Для поиска по уже имеющимся данным это создает лишний барьер. После решения по OCR стоит пересмотреть зависимость.
5. **Плану не хватает явной привязки требований к задачам.** Нет отдельной задачи на выгрузку подбора, не разделены получение реальных стандартов и генерация учебных данных. Нужна простая матрица «требование — задача — ответственный — проверка — статус».
6. **Роли заказчика и аналитика совмещены у Деканозова И.М.** Это допустимо для учебной команды, но стоит явно определить, кто независимо подтверждает эталоны, качество и приёмку.
7. **В уставе остаются шаблонные места.** Пусты вехи и подписи, в разделе SMART нет отдельного пункта Time-bound, хотя срок указан в другом разделе. Формат даты в заголовке обозначен MM/DD/YYYY, фактические даты записаны как DD/MM/YYYY. Фразу «без лицензионного ПО» лучше уточнить как «без необходимости приобретать платные лицензии».
8. **Презентация требует отдельной доводки оформления и иллюстраций.** На слайде 6 мелкий скриншот таблицы плана обрезается границей слайда, на слайде 11 подписи под изображениями тесно примыкают друг к другу. Скриншоты плана на слайдах 6–8 отражают прежний состав исполнителей, их нужно переснять из обновленного MPP. В этом изменении содержание слайдов 3–15 сохранено; отмеченные места требуют следующей редакции.

## Запуск и передача проекта

Сохраненная `.venv` не переносится на этот компьютер: `pyvenv.cfg` указывает на `C:\Program Files\Python311`, а запуск ее `python.exe` сообщает, что Python не найден. В README также остался путь `C:\Users\MaX\Desktop\Codex`. Зависимости удалось использовать с установленным Python 3.11 через отдельный путь к пакетам для проверки, но это не полноценная инструкция установки.

Для передачи следует создавать окружение заново из `requirements.txt`, использовать относительный путь к папке приложения и проверить установку в чистом окружении. В исходном архиве 2721 элемент, из них 2669 относятся к `.venv`. Архив лучше собирать без `.venv`, `__pycache__` и служебных результатов проверки. До правки README прикладные файлы архива совпадали с распакованной папкой; исходный ZIP сохранен как получен и не включает добавленный раздел команды.

Файл `data/codex.db` сейчас представляет учебный набор. Перед демонстрацией на других данных нужна резервная копия. Автозагрузка на старте выполняется только при пустой таблице стандартов; добавление файла в папку и перезапуск уже заполненной системы не заменяют действие «Перепарсить», несмотря на формулировку README.

## Предлагаемый порядок следующей работы

1. Исправить потерю ручных правок, проверку JSON и разбор параметров при создании.
2. Определить устойчивые идентификаторы записей, правила повторного импорта и сохранности подборов.
3. Добавить обработку ошибочных загрузок и честные статусы документов.
4. Согласовать сценарий подбора, критерии, единицы измерения и необходимость OCR, затем реализовать фильтры и выгрузку.
5. Проверить независимую разметку реальных документов, показывать покрытие оценочного набора рядом с точностью.
6. Согласовать даты и фактический прогресс в плане, обновить презентацию и подготовить руководства и протокол приёмки.

Предложенное распределение: Губаз Р.Д. — серверные исправления и интеграция; Титоренко Д.О. — формы, фильтры и показ ошибок; Каримов Д.Н. — реальные документы, поля и эталоны; Симсим А.Б. — проверки и протокол; Деканозов И.М. — требования и архитектурные решения; Тарасов М.К. — согласование объема, сроков и приёмки. Это предложение для дальнейшего планирования, а не запись о выполненных работах.
